# AGENTS.md

## Purpose

This file defines repository-wide instructions for Coding Agents working on this project.

More specific instructions may later be introduced by nested `AGENTS.md` files inside individual modules.

## Before Making Changes

Before modifying the repository:

1. Read this file.
2. Read `docs/README.md`.
3. Read documentation relevant to the task.
4. Inspect the current repository state instead of assuming documentation is perfectly up to date.
5. Prefer extending existing conventions over introducing parallel structures.
6. Check `.agent/note/` for relevant project knowledge when applicable.

## Documentation

Documentation is part of the implementation.

When a change affects documented behavior, architecture, workflows, interfaces, engineering decisions, or development processes, update the corresponding documentation in the same change.

Do not keep important project knowledge only in chat history, issue comments, or temporary Agent context.

Documentation maintenance rules are defined in:

`.agent/skills/documentation/SKILL.md`

## Documentation Validation

Before completing changes that affect documentation, run the repository documentation check.

Use the canonical package script:

`docs:check`

The package manager adopted by this repository is pnpm, so the command is:

```bash
pnpm docs:check
```

A change with failing documentation checks is incomplete.

## Source of Truth

Avoid duplicating the same information across multiple documents.

Each important concept should have one canonical location.

Other documents should link to that source instead of copying its contents.

## Bilingual and multilingual documentation

Chinese is the primary documentation language.

Most documents that require bilingual maintenance follow:

- `<name>.md` is the canonical Chinese version.
- `<name>.en.md` is the corresponding English version.

The two files are treated as one logical document: when you update one, check whether the other needs to be synchronized, and vice versa. If the two versions ever conflict, the Chinese version wins — fix the English version. Do not produce low-quality machine translation; the English version should read naturally and accurately express the meaning of the Chinese version.

The repository root README is the exception: it is maintained in the eight languages the DSH client ships — Chinese, English, Japanese, Spanish, French, German, Russian, and Brazilian Portuguese. `README.md` stays the canonical Chinese edition, and the other seven are `README.en.md`, `README.ja.md`, `README.es.md`, `README.fr.md`, `README.de.md`, `README.ru.md`, and `README.pt.md`. All eight are one logical document: when one changes, synchronize the other seven, keep the same heading and fenced-code-block structure, and cross-link all eight in the language selector. Chinese remains authoritative; if a translation conflicts, fix the translation. Non-Chinese editions link to English documentation when that language has no translated counterpart.

Other README documents and formal documents under `.agent/note/` keep the Chinese/English pair. Do not create empty `.en.md` or other language files for document types unless multilingual maintenance is actually needed.

The changelog is maintained as a bilingual pair too (`CHANGELOG.md` / `CHANGELOG.en.md`): it is a user-facing document that ships inside the npm tarball alongside the READMEs, so an English reader must not hit a Chinese-only release history. Other types — ADRs, plans, reference, and troubleshooting entries — stay Chinese-only unless a real need appears.

## Current Project State

The project is an out-of-tree DSH plugin bundle (`@dsh-electron/dsh-plugin-multi-root-workspace`) that widens the workspace sandbox scope from one root to a primary root plus N additional roots, without modifying any upstream package.

Milestone M1 (bundle composition and empty-root pass-through) is complete and verified: the plugin installs through `dsh plugin`, replaces the two provider rows, and behaves exactly like an uninstalled harness while no additional root is configured. See `docs/plans/completed/2026-09-12-m1-composition-and-passthrough.md` for the evidence and for the T0 findings.

Milestone M2 (additional roots and dialect grants) is complete and verified: a registered additional root is enforced both by the in-process fence and by the host kernel dialect (Seatbelt / bwrap / Landlock) through one shared scope, the cross-provider allow matrix is pinned by tests, the workspace topology reaches the model through a runtime-context contribution, and the empty-root behavior stays byte-identical to an uninstalled harness. See `docs/plans/completed/2026-09-12-m2-additional-roots-and-dialect-grants.md`. Dialect grants are widened by recognizing the profile `super.confine` produced and cloning its grant spelling — never by deep-importing upstream internals (`docs/decisions/ADR-0003-dialect-grant-widening.md`).

Fifteen invariants that must survive future changes:

1. **Re-resolving a path is not re-authorizing it.** A registration carries the canonical directory it was granted for (`recordedPath`); `ctx.multiRootScope` grants it only while `canonicalPath(path)` still equals that value, and reports `redirected` otherwise. Never make a grant follow a replaced directory or symlink.
2. **One write path, serialized.** Registry mutations run their whole read → validate → persist sequence inside the per-primary-root queue (`serialize`); the storage domain only serializes individual writes. Do not read a snapshot outside the queue.
3. **One revalidation entry point.** `registry.refresh()` re-stats, re-resolves, re-judges, republishes the scope, and writes nothing; the command's `list` and the panel's `list` both call it, and listing must remain enough to notice a directory that disappeared. `publish` stays idempotent. `refresh()` also retries the store-wide authority lease so a waiting process can take over after the previous holder exits.
4. **One response shape per panel endpoint.** `src/contract.ts` owns the endpoint → response mapping (`reveal` answers `{ revealed }` and every root-management endpoint answers a `RootsView`), and both halves validate the wire shapes at runtime. Local file browsing does not travel this channel: the Files-tab fork talks to the host `workspaceFiles` Remote namespace directly, and `src/workspace-files.ts` routes and bounds it — explicit-path reads refuse a path lexically under a registered-but-withheld root, `list` and directory `changes` refuse a canonical selected directory that sits under one (the fallback branches check the requested spelling and the resolved canonical target together), and `search` refuses a canonical session root that sits under one, all with `workspace-file/outside-workspace` (upstream carries no read confinement of its own). Remote browsing does travel it: the same panel channel carries `remoteFiles.list` (bounded directory listing with 17 stable error codes) and `remotes.waitForAuthorizationChange` (authorization metadata lease), with `src/remote/files-contract.ts` validating both wire shapes and `src/remote/files-service.ts` owning the dual ordered admission; the browser bundle imports no SSH code.
5. **The client-graph anchor stays.** The web client-module scan reads this package's `dsh.client` only from a loader row mounted at the bare package name — subpath rows are never client rows. `cordis.patch.yml` must keep the `multi-root-client` row (`name` = the bare package name, backed by the barrel's no-op `apply`), or `lib/client.js` never reaches the browser and the `sidebar.footer.action` registration silently disappears. See `docs/troubleshooting/client-bundle-not-in-boot-graph.md`.
6. **One Registry storage owner per store; shared Hosts use ordered admission.** Only the process holding the store-wide kernel lease opens the JSON domain. With `sharedStorageRoot` (enabled by the bundle), other Hosts use kernel-authenticated IPC through their Registry facade; each new operation and every mutation are ordered at the owner, including its own calls. Scope snapshots and notifications never authorize a new operation alone. Without admission, or on uncertainty, preserve negative boundaries and allow only the established primary-root fallback (no shared temp). Synchronous confine/spawn keep their return shape and consume a short-lived admission; cached argv this host did not mint — or minted under a superseded publication — and expired async descendants cannot reuse it. `sharedStorageRoot` is required: the single-process mode was removed, and a registry row without it is `config-invalid` and grants nothing (ADR-0028). Unwrapped upstream services that spawn confined commands outside an admission get primary-only writes by design: an unadmitted `confine` already mints the clamped profile, and that mint may launch only while the publication it was computed from is still current (the minted-profile ledger, ADR-0035). The ledger only accepts primary-bounded forms — `clamped` and `read-only`; `ambient` mints (`restrictedExecution`'s ambient-minus-denies, or any mint whose scope was not proven unavailable) may live only inside a live admission frame and die frameless. A mint stamps its dispatch-time publication — one whose probe completes after a real publication landed stays refused — and an admission frame that has already expired never bequeaths one either: a profile carrying real grants dies with its operation instead of demoting into the ledger. Argv minted elsewhere, under a superseded publication, or outliving its admission stays refused. Teardown remains inside the authority-transition queue: drain mutations → close domain → release lease. See `docs/decisions/ADR-0025-shared-registry-authority.md`, `docs/decisions/ADR-0024-registry-operation-admission.md` and the historical ADR-0007. Platform evidence belongs in the existing progress ledger.
7. **The compatibility gate is a precondition, not a diagnostic — and the provider rows are the exception that keeps the profile alive.** `multi-root-providers`, `multi-root-registry`, `multi-root-instructions`, `multi-root-lsp`, `multi-root-workspace-files` and `multi-root-process-fence` all inject `multiRootCompat`, and cordis will not start a row whose injected service is missing — so an unsupported or mixed installation makes those gated rows simply not exist. Keep that injection on any new row that widens authority. From `0.2.2-alpha.3`, `patchText`, `deleteFile`, and both `moveFile` endpoints must pass the same fs fence and a single Registry admission; see `src/compat/fs-patch.ts`. `multi-root-fs` and `multi-root-sandbox` deliberately do NOT inject the gate: their widening is scope-driven and the gated registry can never populate the scope on a refused installation, so they degenerate to the upstream providers — and because upstream `fs-sandbox`/`sandbox` are already disabled by the patch, gating them would instead take `ctx.fs`/`ctx.sandbox`/`ctx.shell`/`permissionPresets` down and brick the profile (this was the `permissionPresets/catalog` failure: a false `mixed` verdict plus gated providers). A refused gate must degrade to "plugin not installed", never to a dead profile — and never to a widened one, so do NOT add gate-free widening: the scope stays empty without the registry. Version-dependent code belongs only in `src/compat/`, and it must probe *structure* (is the return value thenable? which renderer name is exported?) rather than compare version strings; packages the plugin never loads at run time (host-mounted services, type-only peers) must not testify from a plugin-private copy — see `HOST_SERVICE_PACKAGES` vs `RUNTIME_OPTIONAL_PACKAGES` vs `RUNNER_ANCHORED_PACKAGES` in `src/compat/dsh-version.ts` (the last is for copies executed by the standalone Windows ACL runner, inspected from the `dsh-sandbox-local` anchor). `DSH_MULTI_ROOT_COMPAT=warn` has exactly one legitimate caller, the upgrade lane. Promoting a release is a human act: a green upgrade run is evidence, never authorization. See `docs/decisions/ADR-0009-dsh-compat-contract.md`.
8. **Instructions are user context, never system authority, and revocation is explicit.** `multi-root-instructions` injects each additional root's **top-level** instruction file — and the instruction files of the subdirectories the session has worked in — from `agent/pre-step` as a `form: 'instructions'` user message (source kind `plugin` through session format 3, and this plugin's own `multi-root-workspace` from format 4, which rejects `kind: 'plugin'`) — not through `systemPrompt`, and not from a lifecycle event. Message construction loads the optional peer `@deepseek-ai/dsh-llm` **on demand** through `src/compat/llm-message.ts`, never with a static value import: the barrel is the module the carrier loader row mounts, so its load-time dependency set must equal the required-package set. Discovery is pinned to the root (`projectRoot` is the root, and every candidate must be canonically inside it), which is what keeps `$DSH_HOME`, the primary root (its own nested files included), and any ancestor from being injected a second time. The byte budget is shared across all additional roots, not per root. Touches come from the persisted `session/event` feed: a `tool/call` is paired with its `tool/result` by call id, and only a **successful** `read` / `write` / `edit` makes the directory chain from the root down to the touched file worth examining — a failed call never does. The directories a single touch makes worth examining are the touched file's parent directory and every ancestor of that parent up to the additional root, so an intermediate directory's `AGENTS.md` is visible too. Delivery state is per session and per scope (root + relative directory + file name) and lives in process memory, so after a resume this row may re-tell instructions it already told. When a root is removed, disappears, or is `redirected`, and when a delivered file vanishes, emit an explicit revocation or withdrawal: the earlier instructions are still in the conversation, so going silent does not retract them. With zero additional roots this row must contribute nothing at all. Nested discovery for the **primary** root stays upstream's job, on both supported releases. Resume replay (consumed by the optional Auto Review context) keeps a Host-projection chain and a deprecated-legacy chain side by side: the `stateVersion` the Host registers its working-directory projection at (`1` through the `0.2.2` line, `3` from `0.2.3`, read through the public projection checkpoint) proves structurally which directory-event generation it folds — even when a Session entered another directory and returned and both chains therefore end together — and the chain-end comparison remains the fallback when no version is readable; relative activity that neither evidence can settle is skipped instead of being attributed; absolute paths and the whole-log OPS validation are unaffected. See `docs/decisions/ADR-0010-additional-root-instruction-scope.md`.
9. **Panel authority is host-derived from the session.** Every panel request requires `sessionId`; `resolvePanelPrimaryRoot` looks up `ctx.get('sessions')?.get(sessionId)` and returns `session.header.cwd` verbatim — the Registry/scope key is always the upstream primary spelling via `primaryKey()` (lexical only, never re-resolved); canonical paths are geometry only, so a renamed-and-symlinked primary keeps its record set and deny boundaries (ADR-0028). There is no client `primaryRoot` field and no `sandboxPolicy` fallback. A missing or unknown session is rejected; a client with no current session shows "No active session" and does not call the host. The rejection code splits on durable existence — `sessionPersistence.stat` finding a snapshot (writer-held by another Host or mid-resume), or the resolver succeeding on a catch-time re-run (a race that resolved after the throw), yields `session-not-live`; a live session that still cannot name a root (missing/non-absolute cwd) and anything unprovable keep `session-not-found`; the classification happens once at the dispatch catch (ADR-0008 amendment). The `/workspace-folders` command still uses `invocation.agent.session` (trusted host context). See `docs/decisions/ADR-0008-panel-session-derived-authority.md`.
10. **The writable set is the only authorization that reaches enforcement.** `resolve()`'s `writableRoots` = read-write members ∩ the effective tool cap (the `AsyncLocalStorage` flag set at `tools/execute` dispatch entry from `exec.name` — nesting only narrows, and outside any dispatch a non-empty `toolAccess` means capped). Only that set reaches the fs fence, every kernel dialect, and the Windows root-set SID. Membership projections (`additionalRoots`, `roots`) are unaffected: a read-only root stays readable and routable, it just never receives write authority. Never widen `writableRoots` past this intersection, never read tool identity from model arguments, and never treat read-only as read confinement. The single approved exception: a one-shot `danger-full-access` escalation the user allowed on THIS call (noted on the dispatch's tool-cap store by the wrapped `approval.request`, pinned by callId + the `escalate sandbox to danger-full-access:` reason prefix) lifts the read-only-root and per-tool-cap refusals for that call alone — nested, sibling and later dispatches get fresh `false` stores, a standing Full-access session can never produce the marker, and `protectedHome` plus the `unavailable`-authority clamp hold regardless (`docs/decisions/ADR-0036-approved-escalation-override.md`). Under `danger-full-access` the deny side is symmetric: once restrictions apply (a non-empty PRE-override deny set or an unavailable authority), `resolve()` also appends the configured `dshHome` to `deniedRoots` as `protectedHome` — `$DSH_HOME` holds the store, the lease and user profiles, and deny wins even when the primary root sits inside it. See `docs/decisions/ADR-0013-per-root-and-per-tool-access.md`.
11. **The provider brand gate prevents foreign-provider widening.** `ctx.fs` and `ctx.sandbox` must carry this plugin's `Symbol.for('@dsh-electron/dsh-plugin-multi-root-workspace/provider')` brand; `multi-root-providers` checks it at init and the registry, instructions, LSP and workspace-files rows inject it, so any foreign provider — regardless of composition order — leaves the multi-root rows absent and the scope empty. Never replace the brand check with instanceof or cordis-private state, and never warn-and-continue on a conflict. See `docs/decisions/ADR-0014-root-limit-and-provider-conflict.md`.

12. **OPS adaptation observer rules.** The experimental `multi-root-ops-compatibility.enabled` setting defaults to `false`; only an explicit `true` on a DSH `0.2.*` host with modern Settings enables the OPS-specific execution, activity, and Review adapters. DSH `0.1.*` stays off even with `enabled: true`; OPS does not support the legacy Settings UI (ADR-0029 version-scope amendment). A missing or disposed settings service means off, not an implicit opt-in. Mode changes invalidate pending preparation, activity candidates, and Review snapshots; an already-entered execution domain retains its protection until completion. Disabling this adaptation must not disable native filesystem, shell, PTC, or PTY fences. Tool interception must register listeners `global: true` so agent-scoped carriers are observed. When wrapping subprocess dispatch, wrap the service object returned by `ctx.get('subprocess')`, never a traced service proxy. Cache-tmpdir admission requires `realpath` resolution: `canonicalPath` silently falls back on missing paths and must not be substituted there. A result observer must never alter the business result; fingerprint/snapshot failures in the active mode mark activity incomplete and warn. P5 supersedes the initial WW/RO pass-through: with the adaptation enabled, deny-bearing WW/RO OPS calls and authority-unavailable OPS calls in every mode refuse before preparation. The scope-owned subprocess guard survives fence removal; do not authorize maintenance from filenames, cwd, private stdin, a cached/expired launch handoff, or the unadmitted mint ledger — the ledger can prove an argv was minted here, never that an admission paid for it. See the P5 amendment and final scope in ADR-0029. P6 accepts only the experimental conservative subset; the remaining P5 capabilities and full compatibility recovery are indefinitely deferred, excluded from final acceptance, and must not be restarted or promoted to stable implicitly.

13. **Session identity is the origin, never the effective working directory.** `session.header.cwd` is the only source of Registry/scope keys (through `originDirectory` / `policyOriginRoot` in `src/compat/session-directory.ts`); `sandboxPolicy.resolve({session}).workspaceRoot` may now be the effective directory and is only the upstream enforcement boundary and path base. From `0.2.3-alpha.1` upstream resolves that policy root through the `workingDirectory` service, so a scope-table lookup by the effective spelling yields an empty deny set: a registered `read-only` root the moved Session lands inside can become writable under `workspace-write` and `toolAccess` caps disappear. Derive the origin before the first await, keep `policy.workspaceRoot` for mode/geometry, and accept both the new `workspace-root/change` (stateVersion 3) and the deprecated `working-directory/change` in resume replay. The upstream primary boundary moving with the effective directory is intentional (the Host Worktree service needs it); never pin it back to the origin, and never let that move re-key the plugin's own additional-root grants or their deny set. See the ADR-0012 amendment. When the registry authority is unavailable, the process clamp and the Files wire-origin fallback must derive that same origin (a moved Session never gains its effective directory as a clamp grant), a stored Session's origin comes from its durable header rather than the projection-cached wire root, and instruction replay is limited to the pre-mount seed prefix so post-resume activity keeps the Host's effective directory. Windows ACL widening still cross-checks the upstream profile against `policy.workspaceRoot`; only the grafted grants use the origin.

14. **A Files tree node's identity is its root reference plus authorization incarnation, never a path spelling.** `RootRef` (`primary` / `additional` / `remote`) plus the root-relative path identifies a tree node; display strings, remote path spellings and `user@host:port/path` are metadata only — never key into tree, search or navigation state, never authorize, never flow back into `openResourceIn` / `fileAddressFor` / `workspaceFiles`. Keys include the session, tab/pane and authorization incarnation, so a re-authorized environment retires its old state instead of reviving it and two environments sharing a path spelling cannot collide. Remote browsing is a per-binding opt-in and a **deployment assertion** (`directoryListing: 'stable-path'` with `read`), not a runtime proof: the host admits before and after each SSH I/O with a UI-read-only purpose, bounds entry count and serialized bytes, refuses symlink swaps and root redirection before listing, never reuses a Helper object (`dev:ino`) grant or a `remote_copy` SFTP channel for browsing, and fails closed on Broker without a directory stream. Only the seven authorization codes invalidate the remote tree; everything else stays an inline row error, and hiding the tab drops the takeover without memoizing listings, expansion or scroll. See `docs/architecture/file-browsing-providers.md`, ADR-0052, and `docs/plans/completed/2026-11-24-provider-remote-file-tree.md`.

15. **Remote preview is its own authorization and an opaque resource, never a local path or a second viewer.** `filePreview: 'stable-path'` is an independent binding opt-in never inherited from `read` or `directoryListing`; its option appears only while `read` and the Files listing are both enabled, and saving the field changes the binding digest, so the binding returns to `withheld` until it is registered again. The SSH provider's optional `preview` port may route only ordinary file rows, and the host revalidates every condition server-side. A resource address is an in-memory random UUID that carries no session, environment, root, authorization or path facts and has no persisted lookup; content bytes never travel through `ctx.resources`, and a revoked, replaced, closed or browser-reloaded address renders as explicitly expired instead of reviving. Content comes from the single strict `remoteFiles.read` over one Connection binary attachment — one complete read, no stat or range, 2 MiB enforced on both sides and refused whole, never truncated — and the host runs initial/recheck/final ordered Registry admissions on one owned SFTP v3 channel, validates the canonical root and every ancestor plus the regular-file type and size, and returns bytes only after closing that channel and completing the final proof. Preview is personal-custody SFTP only; Broker, team and hardened tiers fail closed, and `sftp-binary-v1` is issued on exactly the SSH browsing matrix — `src/compat/remote-file-preview.ts` reads `SUPPORTED_SSH_RELEASES` directly rather than keeping a second preview release table, so a host below the SSH floor never issues it (such a host cannot select a remote root in the first place). The widened issuance is backed by the per-release production acceptance runs recorded in the plan's review-addendum section. The viewer is a plugin-owned visual adaptation of the host document preview, not a fork or mount of upstream viewer internals, and it stays read-only: no editing, writeback, download, watch, polling, search, diff, LSP or open-in-app. See `docs/architecture/remote-file-preview.md`, ADR-0053, and `docs/plans/completed/2026-11-27-provider-remote-file-preview.md`.
