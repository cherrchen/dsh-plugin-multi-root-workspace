## Что и зачем

По умолчанию [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) считает каталог, в котором создаётся новое рабочее пространство, основным каталогом агента; в режиме чтения и записи по умолчанию (`workspace-write`) область чтения и записи песочницы тоже ограничена только этим каталогом. Плагин расширяет область рабочего пространства DSH до «одного основного корня + N дополнительных корней».

Не каждый проект — monorepo. Настоящий проект разработки обычно состоит из нескольких независимых Git-репозиториев, и работа с ними раньше означала постоянные переключения между сеансами. Похожие инструменты давно умеют добавлять несколько папок в одно рабочее пространство. Этот плагин даёт ту же возможность DSH: зарегистрируйте другие репозитории как дополнительные корни, задайте каждому доступ только для чтения, чтение и запись или наследование текущих разрешений сеанса — и агент сможет работать в них в пределах выданных разрешений.

- **Нативные инструменты**: в локальных рабочих пространствах Agent по-прежнему использует нативные `read` / `write` / `edit` / `bash`; у него просто появляется несколько дополнительных каталогов для работы.
- **Разрешения действительно соблюдаются**: каждый дополнительный корень можно сделать доступным только для чтения, для чтения и записи или наследующим разрешения текущего сеанса; ограничения реально применяет системная песочница, а не напоминание модели в промпте. К файловым операциям агента и командам bash применяются одни и те же разрешения; процессы, запущенные другими плагинами, под эту гарантию не попадают.
- **Просмотр дополнительных корней на вкладке Files**: в заголовке вкладки Files можно переключаться между основным корнем и любым дополнительным; дерево каталогов, открытие файлов, открытие во внешнем приложении, контекстные меню, автообновление и поиск работают так же, как в основном корне, а навигатор в предпросмотре документа также переходит к корню, в котором находится файл. На более старых версиях хоста часть этих действий может быть недоступна, и дополнительный корень отображается так, как это делает сам хост.
- **Skills в дополнительных корнях**: автоматически обнаруживаются `.dsh/skills` и `.agents/skills` в дополнительных корнях, вызываются они как `/alias:skill-name`; для каждого корня есть отдельный переключатель, по умолчанию включён.
- **Auto Review (экспериментально, по умолчанию выключено)**: после включения вручную в менеджере плагинов автоматическая проверка также видит структуру каталогов дополнительных корней, уровни доступа и файлы инструкций и включает дополнительные корни в проверку.
- **Подсказки Worktree (экспериментально, по умолчанию выключено)**: если основной корень — это Git worktree, плагин предложит добавить другие worktree того же репозитория как дополнительные корни; регистрация происходит только после вашего подтверждения, автоматически ничего не добавляется и не удаляется.
- **Удалённые среды SSH (экспериментально, по умолчанию выключено, не выпущено)**: переключатель «Удалённые среды SSH» на карточке плагина (предупреждающая метка «Экспериментально», для включения требуется подтверждение рисков) открывает удалённую плоскость управления Registry в соответствии с манифестом развёртывания; вместе с предоставленной при развёртывании аттестацией broker она даёт Agent доступ к `remote_copy` / `remote_bash`; Workspace Folders показывает список удалённых рабочих пространств и отдельный диалог управления SSH-средами, а каждый вызов по-прежнему проходит допуск Registry. Пока переключатель выключен, никаких видимых модели удалённых возможностей нет.
- **Не зарегистрирован — значит не установлен**: без дополнительных корней поведение полностью совпадает с неустановленным плагином; ошибка конфигурации приводит к явному сообщению об ошибке, а не к незаметной деградации.

Текущая версия — `v0.1.23`. Видимые пользователю изменения каждой версии см. в [CHANGELOG](./CHANGELOG.en.md); прогресс и состояние выпусков — в [реестре прогресса дорожной карты](./docs/plans/active/2026-09-12-multi-root-workspace.md#进度总账).

## Быстрый старт

Плагин опубликован в [npm](https://www.npmjs.com/package/@dsh-electron/dsh-plugin-multi-root-workspace). Для профилей командной строки (`web` / `headless` и т. п.) установка занимает две команды:

```sh
dsh plugin --profile web add @dsh-electron/dsh-plugin-multi-root-workspace
dsh --profile web       # --profile выберите под свой способ запуска; значения см. в документации DSH
```

**Пользователи DSH Desktop**: введите `@dsh-electron/dsh-plugin-multi-root-workspace` на странице плагинов, чтобы установить его; если при запуске возникает ошибка, перезапустите DeepSeek Harness Desktop.

Другие способы установки (tarball, GitHub, локальный исходный код) описаны в разделе [Установка](#установка).

Чтобы добавить дополнительный корень, выполните в сеансе:

```text
/workspace-folders add ~/code/another-repo [--inherit|--read-only|--read-write]
```

## Установка

Плагин устанавливается двумя способами: из командной строки (CLI) или через менеджер плагинов в графическом интерфейсе Web / Desktop. Достаточно любого из них.

### Установка через CLI

`dsh plugin` поддерживает четыре источника установки; ниже показан профиль `web`, для `headless` и других профилей CLI всё аналогично. **Пользователи DSH Desktop**: профилем `desktop` нужно управлять через CLI `dsh`, встроенный в DeepSeek Harness Desktop; шаги приведены в конце этого раздела.

| Источник | Команда | Примечание |
| --- | --- | --- |
| Реестр npm (рекомендуется) | `dsh plugin --profile web add @dsh-electron/dsh-plugin-multi-root-workspace` | Готовые артефакты, работают сразу после установки |
| GitHub | `dsh plugin --profile web add github:cherrchen/dsh-plugin-multi-root-workspace` | Собирается из исходного кода автоматически при установке; в `allowBuilds` должен быть точный ключ этого пакета, рекомендуется закрепить версию |
| tarball | `dsh plugin --profile web add ./dsh-electron-dsh-plugin-multi-root-workspace-<version>.tgz` | Готовый офлайн-пакет, подходит для внутренних сетей и работы без подключения к сети |
| Установка из исходного кода | `dsh plugin --profile web add /path/to/package/dsh-plugin-multi-root-workspace` | pnpm `link:` на локальный checkout, подходит для разработки и отладки; `allowBuilds` не нужен |

#### Установка из npm (рекомендуется)

```sh
dsh plugin --profile web add @dsh-electron/dsh-plugin-multi-root-workspace
```

Устанавливаются готовые артефакты.

#### Установка из tarball

```sh
pnpm pack @dsh-electron/dsh-plugin-multi-root-workspace
# или скачайте из ассетов GitHub Release, например:
# https://github.com/cherrchen/dsh-plugin-multi-root-workspace/releases/download/v0.1.23/dsh-electron-dsh-plugin-multi-root-workspace-0.1.23.tgz
dsh plugin --profile web add ./dsh-electron-dsh-plugin-multi-root-workspace-0.1.23.tgz
```

Это тоже готовые артефакты; вариант подходит для доставки во внутренние сети или офлайн-среды.

#### Установка с GitHub

```sh
dsh plugin --profile web add github:cherrchen/dsh-plugin-multi-root-workspace
```

Установка с GitHub получает исходный код и автоматически собирает его при `add`, ручная сборка не нужна; pnpm блокирует `prepare` самого пакета и выводит одну строку с точным ключом (с указанием источника и коммита). Скопируйте эту строку без изменений в `allowBuilds` и повторно выполните `add`:

```yaml
allowBuilds:
  # Ключ и значение берутся из примера «Add the package to allowBuilds» в ошибке pnpm;
  # ключ только с именем пакета, без источника и коммита, для git-источников не действует.
  '@dsh-electron/dsh-plugin-multi-root-workspace@github:cherrchen/dsh-plugin-multi-root-workspace#<commit>': true
```

Рекомендуется закрепить версию (например, `#v0.1.23`), чтобы последующие отправки не могли незаметно изменить то, что реально выполняется:

```sh
dsh plugin --profile web add github:cherrchen/dsh-plugin-multi-root-workspace#v0.1.23
```

#### Установка из локального исходного кода

```sh
git clone https://github.com/cherrchen/dsh-plugin-multi-root-workspace.git
cd dsh-plugin-multi-root-workspace
export CI=true
pnpm install
pnpm build
dsh plugin --profile web add /path/to/repo
```

> [!TIP]
> Если `dsh` отсутствует в PATH (например, вы запускаете DSH из исходного репозитория), замените `dsh` в команде на `pnpm dsh`.

#### Установка со встроенным CLI DeepSeek Harness Desktop

DeepSeek Harness Desktop позволяет установить глобальную команду `dsh` через пункт меню приложения «Управление командой dsh…»; для профиля `desktop` в DeepSeek Harness Desktop используйте эту команду.

1. Полностью закройте Desktop, включая значок в трее.
2. Новая установка:
   ```sh
   dsh plugin --profile desktop add @dsh-electron/dsh-plugin-multi-root-workspace@0.1.23
   ```
3. Уже установлен, но нет записи в bundle: сначала `remove`, затем `add` (повторный запуск только `add` не добавит запись):
   ```sh
   dsh plugin --profile desktop remove @dsh-electron/dsh-plugin-multi-root-workspace
   dsh plugin --profile desktop add @dsh-electron/dsh-plugin-multi-root-workspace@0.1.23
   ```
4. Откройте `$DSH_HOME/profiles/desktop/package.json` (если `DSH_HOME` не задан, обычно `~/.dsh/profiles/desktop/package.json`) и убедитесь, что `dsh.profile.bundles` содержит этот пакет.
5. Снова откройте Desktop (холодный запуск).

Если `add` завершается с кодом 0, но плагин не попадает в `dsh.profile.bundles`, выполните `remove` + `add`. Причина конфликта при горячем включении, запись о воспроизведении и расследование того, кто фактически пишет в профиль, — в разделе [устранение неполадок](./docs/troubleshooting/desktop-install-missing-bundle.md).

### Установка через менеджер плагинов Web / Desktop

И в Web, и в Desktop установка выполняется со страницы «Плагины» в боковой панели: нажмите «Добавить плагин», введите `@dsh-electron/dsh-plugin-multi-root-workspace` и установите. После установки нажмите «Включить сейчас» — одна лишь установка не включает плагин. Если на странице «Плагины» нет пункта «Добавить плагин», установите через CLI, как описано выше.

После установки или включения необходимо перезапустить приложение DeepSeek Harness: полностью закройте Desktop (включая значок в трее) и откройте заново, а для Web перезапустите процесс `dsh web`. Горячее включение плагина в работающем приложении может выдать ошибку повторной регистрации `fs` / `sandbox`; после перезапуска плагин загружается нормально.

## Использование

### Команда

```text
/workspace-folders [list]                                                   # перечислить основной и дополнительные корни (с доступом и состоянием каждого)
/workspace-folders add <absolute path> [--inherit|--read-only|--read-write] # без пути открывается системный выбор каталога; новый корень по умолчанию inherit
/add-dirs [absolute path] [--inherit|--read-only|--read-write]              # сокращение для /workspace-folders add
/workspace-folders access <order|path> inherit|read-only|read-write         # переключить уровень доступа (расширение требует, чтобы корень был доступен сейчас)
/workspace-folders skills <order|path> on|off                               # включить или выключить Skills этого корня, не меняя права записи
/workspace-folders alias-id <order|path> <kebab-case>                        # изменить стабильное пространство имён Skill
/workspace-folders alias <order|path> [alias]                               # без псевдонима существующий псевдоним очищается
/workspace-folders remove <order|path>                                      # номер — это номер из вывода list
/workspace-folders reveal <order|path>                                      # показать в файловом менеджере
/workspace-folders isolate-profiles [--apply]                               # проверить (с --apply — записать) способ импорта зависимостей профиля
/workspace-folders help                                                     # показать справку по команде
```

- Пути можно заключать в кавычки, `~` раскрывается; дубликаты, пути, вложенные в существующий корень, сам основной корень, а также защищённые пути, такие как `$DSH_HOME` / каталог хранения Registry, отклоняются.
- `remove` / `access` / `alias` / `reveal` принимают `номер|путь`; `add` без пути открывает системный выбор каталога (если хост его предоставляет), можно также указать только параметр доступа.
- `list` показывает уровень доступа и состояние каждого корня. Если каталог временно отсутствует (`missing`) или заменён ссылкой, ведущей в другое место (`redirected`), регистрация сохраняется, но доступ не выдаётся; после восстановления каталога достаточно выполнить `list` или обновить «Папки рабочего пространства».
- `isolate-profiles` — предполётная проверка для ограниченного полного доступа (Full-access) на Windows: по умолчанию только проверяет `packageImportMethod` каждого профиля под `$DSH_HOME`, а с `--apply` записывает конфигурацию `copy`; он не удаляет `node_modules` и не изменяет существующие зависимости.

### Уровни доступа

| Уровень доступа | Сеанс `workspace-write` | Сеанс `read-only` | Сеанс `danger-full-access` |
| --- | --- | --- | --- |
| `inherit` (по умолчанию для новых корней) | запись разрешена | запись запрещена | без ограничений |
| `read-only` | запись запрещена | запись запрещена | запись запрещена (включая Full-access) |
| `read-write` | запись разрешена | запись разрешена | запись разрешена |

- Новые корни по умолчанию получают `inherit`; изменение прав действует только на последующие вызовы и новые процессы, а уже запущенные процессы и постоянные терминалы сохраняют права, с которыми были запущены.
- Однократное повышение прав `danger-full-access`, одобренное пользователем для отдельного вызова, снимает для этого вызова отказы, вызванные корнями только для чтения и потолком на инструменты; при этом запрет на `$DSH_HOME` и понижение при недоступности Registry продолжают действовать.
- На один основной корень приходится не более 16 дополнительных корней (`maxAdditionalRoots` можно увеличить до 64). Хост может навсегда ограничить инструмент для всех дополнительных корней через `toolAccess` строки `multi-root-scope`, например `{ bash: 'read-only' }` запрещает bash запись в любой дополнительный корень (в основной корень писать по-прежнему можно).

### Skills в дополнительных корнях

- В дополнительных каталогах автоматически обнаруживаются `.dsh/skills` и `.agents/skills`; имена и описания доступны на первом шаге модели, тела загружаются по требованию.
- Основной корень использует `/skill-name`, дополнительные — `/alias-id:skill-name` (в Slash-меню доступно автодополнение); модель вызывает их встроенным инструментом `skill`, поэтому в журнале инструментов могут отображаться внутренние ID.
- У новых корней `inherit` / `read-write` Skills включены по умолчанию, у корней `read-only` — выключены; в диалоге есть переключатель для каждого корня и редактируемый `aliasId` (изменение отображаемого Alias не влияет на `aliasId`). Включение Skills у корня только для чтения не даёт права записи.
- Откройте страницу подробностей Multi-root Workspace на странице «Плагины» в боковой панели: переключатель **Включить Skills дополнительных корней** в карточке настроек управляет всеми дополнительными корнями и по умолчанию включён; после выключения новые обнаружения и вызовы прекращаются, но выбор для каждого корня сохраняется. На Skills, инструкции, LSP, просмотр файлов и разрешения песочницы основного корня это не влияет.

### Подсказки Worktree (экспериментально, по умолчанию выключено)

Если основной корень — корень Git worktree, плагин перечисляет другие worktree того же репозитория как кандидатов в одной карточке-подсказке, включая worktree, созданные ранее терминалом, IDE или forge; если сам сеанс является linked worktree и работает в `workspace-write`, в кандидаты также попадает основной checkout этого репозитория. Обнаружение только читает метаданные Git и не запускает подпроцессы Git, **корни никогда не добавляются и не удаляются автоматически**; в сеансе `danger-full-access` подсказка не показывается. Откройте страницу подробностей Multi-root Workspace на странице «Плагины» и включите в карточке настроек **Включить подсказки Worktree для дополнительных корней** (по умолчанию выключено).

Подсказка — постоянная карточка: можно выбрать «Просмотреть» или «Напомнить позже» (до появления нового worktree / через 7 дней / через 30 дней); кнопка закрытия в правом верхнем углу скрывает только текущую подсказку, и после перезапуска она появляется снова. После закрытия её можно снова открыть из «Подсказок Worktree» рядом с «Повторить» в диалоге «Папки рабочего пространства». Диалог подтверждения построчно показывает путь, ветку и права (по умолчанию `inherit`, можно изменить на «только для чтения» или «чтение и запись»); если кандидатов несколько, можно отметить несколько; строка основного checkout дополнительно поясняет его область: дерево исходников основного checkout, общие config/hooks/refs/objects и административные данные всех worktree, что может затронуть другие checkout того же репозитория. Регистрация действует на уровне рабочего пространства, поэтому **другие сеансы чтения и записи также получат выбранные права**; при подтверждении выполняется повторная проверка, и изменения за это время делают элемент недействительным. В диалоге также можно выбрать «Больше не напоминать».

Если worktree удалён или перемещён, диалог показывает бейдж, но **автоматическая очистка никогда не выполняется**; очистка предлагается, только когда каталог подтверждённо отсутствует и идентичность регистрации совпадает (пакетно или построчно), с подтверждением в диалоге поверх него. Перед очисткой новый каталог по тому же пути может унаследовать старые разрешения — диалог подтверждения раскрывает этот риск.

### Адаптация Auto Review (экспериментально, по умолчанию выключено)

Если нужен контекст проверки с несколькими корнями, включите в списке компонентов страницы подробностей Multi-root Workspace на странице «Плагины» строку Auto Review, выключенную по умолчанию; переключатель «Мультикорневой Auto Review (экспериментально)» в той же карточке настроек равноценен ему и также по умолчанию выключен. Обычная установка не включает Auto Review и не выбирает его автоматически; интеграция действует только в тех точных релизах DSH, которые её предоставляют.

### Удалённые среды SSH (экспериментально, по умолчанию выключено, не выпущено)

Возможность нескольких сред выполнения из Issue #32 поставляется в составе стандартного bundle за экспериментальным переключателем: пункт **Удалённые среды SSH** на карточке настроек на странице подробностей плагина имеет предупреждающую метку «Экспериментально» и **по умолчанию выключен**; для включения нужно прочитать подтверждение рисков (Agent сможет выполнять команды и копировать файлы на настроенных удалённых хостах, а кто хранит учётные данные, зависит от режима хранения учётных данных); отмена или закрытие диалога ничего не сохраняет. Карточка настроек оставляет только переключатель включения; **режим хранения учётных данных** переключается в диалоге «Управление SSH-средами» панели Workspace Folders → «Режим», три режима взаимоисключающие:

- **Персональный (по умолчанию)**: учётные данные хранятся непосредственно в процессе локального Host — **никто не гарантирует, что Agent не получит доступ к ключам**; подходит для личной машины, одноразовой VM или доверенного Agent.
- **Командный**: учётные данные хранятся в отдельной учётной записи broker, а назначением копирования должен быть chroot SFTP; вкладка «Режим» показывает четыре поля broker (manifestPath / socketPath / brokerUid / credentialRoot), которые можно сохранить на месте. Подходит для общей сборочной машины.
- **Усиленный**: broker + квоты/аудит/отзыв + выделенная учётная запись с независимыми процессами записи, настраивается профилем развёртывания; вкладка «Режим» показывает только пояснение и не редактируется.

При включённом переключателе переход на режим с меньшей изоляцией снова проходит через подтверждение рисков. Registry читает источник манифеста в зависимости от режима (personal → `remoteEnvironments.personalPath`; team/hardened → `remoteEnvironments.manifestPath`, по умолчанию `/etc/dsh-ssh-broker/manifest.json`) и строит удалённую плоскость управления. Раздел «Удалённые среды» панели Workspace Folders оставляет только **список удалённых рабочих пространств** (стиль строк дополнительных корней, реальные названия платформ Linux / macOS, регистрация и удаление сохранены) и пункт «Управление SSH-средами…». Сохранённые подключения, SSH-ключи и настройки режима находятся на трёх вкладках отдельного диалога, а новое подключение создаётся в отдельном диалоге, который открывается со вкладки «Подключения». Форма использует примитивы хоста: `Input`/`Button`/`Tag` доступны во всех поддерживаемых выпусках, `Checkbox` используется там, где доступен, а на более старых выпусках заменяется собственным элементом управления с явно заданными стилями; поля располагаются в двухколоночной сетке с постоянными подписями.

**Один проход в персональном режиме** (в диалоге «Управление SSH-средами»): откройте Workspace Folders → «Управление SSH-средами…» → на вкладке «Подключения» нажмите «Добавить подключение» → на шаге 1 диалога выберите источник учётных данных (псевдоним узла ssh-config или управляемые учётные данные; если их ещё нет, создайте их в диалоге «Управление учётными данными» или на вкладке «SSH-ключи»), заполните отображаемое имя, идентификатор среды и платформу, затем `user@host:port` → нажмите «Сканировать и проверить подключение», выберите отпечаток в диалоге подтверждения; после подтверждения подключение сохраняется и автоматически открывается шаг 2 → на шаге 2 проверьте Node, установите helper (необязательно; можно пропустить для сред только с SFTP), при необходимости свяжите `~/.ssh/config`, введите удалённый путь вручную или через «Выбрать в интерфейсе» и выберите возможности передачи файлов / выполнения команд → «Привязать к проекту» сохраняет обновление среды, создаёт привязку primary и регистрирует её, если helper установлен; «Пропустить» оставляет подключение для последующего завершения на вкладке «Подключения». Секретные поля очищаются при отправке, и ни один ответ RPC не содержит байтов закрытого ключа или пароля.

Инструменты `remote_copy` / `remote_bash` на стороне модели и проекция возможностей в режимах team/hardened дополнительно требуют аттестации изоляции учётных данных broker: блок broker предоставляет развёртывание в выделенном профиле (hardened) или поля вкладки «Режим» (team), и любой сбой на шаге (проверка возможностей SSH, плоскость управления не готова, сеанс `danger-full-access` — отклоняется только в hardened, аттестация) не устанавливает инструменты. Каждый удалённый вызов по-прежнему проходит упорядоченный допуск Registry. Выключение переключателя размонтирует всё удалённое поддерево и возвращает плоскость управления в `disabled` (нет слушателя `remote-1`, нет удалённого домена). Границы защиты по режимам, раскладка файлов и коды отказа RPC описаны в [справочнике по удалённым средам SSH](./docs/reference/ssh-remote-environments.md) (на китайском); шаги развёртывания и отката для team/hardened — в [справочнике по плоскости управления](./docs/reference/multi-environment-control-plane.md) (на китайском).


### Точки входа в интерфейсе

- **Боковая панель и страница нового сеанса**: действие **Папки** внизу боковой панели открывает диалог «Папки рабочего пространства»; начиная с DSH `0.2.1-alpha.3` тот же вход есть справа в строке рабочего пространства на странице нового сеанса (без стрелки, в узком окне — только значок). В диалоге можно добавлять и удалять корни, редактировать псевдонимы и права, включать и выключать Skills для каждого корня, копировать пути, показывать в файловом менеджере, а также обновлять список кнопкой «Повторить» и открывать «Подсказки Worktree».
- **Меню строки рабочего пространства**: в меню `…` строки рабочего пространства и в контекстном меню есть пункт «Управление папками рабочего пространства…»; если текущий сеанс принадлежит этому рабочему пространству, диалог открывается сразу, иначе сначала открывается или переиспользуется пустая страница этого рабочего пространства, а диалог открывается после того, как она станет текущим сеансом.
- **Вкладка Files**: переключатель корня в заголовке переключает основной корень и любой дополнительный; при выбранном дополнительном корне дерево каталогов, открытие файлов, открытие в приложении, контекстные меню, автообновление и поиск по рабочему пространству работают в этом корне, а при возврате к основному корню восстанавливается исходный вид.

### Со стороны модели

Топология дополнительных корней внедряется в системный промпт и обновляется при изменении разрешений; новый инструмент для этого не нужен. Собственные `AGENTS.md` / `CLAUDE.md` дополнительного корня также попадают в контекст по мере необходимости: файл верхнего уровня корня — до первого шага сеанса, файл подкаталога — после того, как этот сеанс **успешно** работал в этом каталоге.

Более подробные инструкции по отдельным функциям см. в [руководстве пользователя по функциям](./docs/guide/user/README.en.md).

## Участие в разработке

Мы приветствуем Issue и PR:

1. Сначала прочитайте [`AGENTS.md`](./AGENTS.md) (правила репозитория) и [процесс разработки](./docs/development/plugin-development-workflow.md) (окружение, команды, матрица поддерживаемых версий, процесс обновления).
2. Создайте ветку от `main`; сообщения коммитов — по conventional commits (`feat` / `fix` / `perf` / `refactor` + scope), см. существующую историю.
3. Перед PR локально должны проходить все проверки: `pnpm lint`, `pnpm typecheck`, `pnpm build`, `pnpm test`, `pnpm docs:check`, `pnpm smoke` (CI выполняет их в том же порядке: сначала build, затем test).
4. Изменения поведения должны в том же изменении обновлять соответствующие документы в `docs/`; восемь языковых версий README в корне поддерживаются синхронно (каноническая — китайская); для инженерных решений с компромиссами добавляйте ADR.
5. Жёсткое ограничение: **не изменять ни один пакет вышестоящего репозитория (deepseek-harness)**; плагин остаётся расширением out-of-tree.

Полные правила приведены в [руководстве по участию](./CONTRIBUTING.md).

## Известные ограничения

### Функциональность плагина

- Файлы инструкций дополнительного корня попадают к модели по мере необходимости: файл верхнего уровня корня внедряется до первого шага сеанса, файл подкаталога — после того, как этот сеанс **успешно** работал в этом каталоге; вложенный файл перепроверяется только при рассмотрении его каталога (файл уровня корня — на каждом шаге, файл подкаталога — если он уже доставлен или появилось новое касание), состояние доставки хранится в памяти процесса (после resume инструкция может быть передана повторно); официально распознаются `read` / `write` / `edit`, а при включённом режиме совместимости OPS инструменты OPS также управляют доставкой через live-доказательства (история OPS без live-доказательств после resume в доставке не участвует). Цепочка инструкций основного корня, как и файл user-global, остаётся за вышестоящим кодом, плагин не внедряет её повторно ([ADR-0010](./docs/decisions/ADR-0010-additional-root-instruction-scope.md)).
- Несколько Host совместно используют один сервис регистрации: хранилищем управляет только один Host, а каждый экземпляр получает допуск на каждую операцию; при разрыве связи новые разрешения для дополнительных корней прекращаются, а после завершения авторитетного процесса управление перехватывается по блокировке ядра. Совместное использование ограничено одной машиной, одним пользователем и одним пространством имён блокировок; в Linux для общего подключения требуется SO_PEERPIDFD, в Windows — один сеанс входа. Старые процессы и PTY сохраняют снимок запуска ([архитектура совместного доступа](./docs/architecture/registry-authority-service.md)).
- Матрица поддержки — это allowlist точных версий: если релиза хоста нет в списке или основные пакеты установлены в разных версиях, строки `fs` / `sandbox` / `registry` / `instructions` / `lsp` / `workspace-files` **не запускаются**, и композиция деградирует до состояния «плагин не установлен» ([ADR-0009](./docs/decisions/ADR-0009-dsh-compat-contract.md)).
- Многокорневой runner Windows наследует частичное применение ограничений вышестоящего кода, требования к каталогам, принадлежащим вызывающему, и условие разделения private temp; уже запущенные процессы сохраняют набор корней на момент запуска, а последующие процессы используют обновлённый набор ([ADR-0011](./docs/decisions/ADR-0011-multi-root-workspace-consumers.md)).
- **Сетевые пути и пути к устройствам в Windows не могут быть дополнительными корнями**: UNC (`\\server\share`), `\\?\`, `\\.\` и подключённые сетевые диски отклоняются при регистрации с `unsupported-path` — capability SID restricted token не позволяет привязать доступ по SMB ([поправка к ADR-0011](./docs/decisions/ADR-0011-multi-root-workspace-consumers.md)).
- **Ограниченная оболочка Windows — это pwsh, без Git Bash**: MSYS не запускается под restricted Low-integrity token (это одинаково для вышестоящего runner и runner плагина и является ограничением вышестоящего кода); ограниченный дочерний процесс вышестоящего runner не получает Ctrl+C, поскольку наследует флаг игнорирования Ctrl+C, а под runner плагина дочерний процесс получает Ctrl+C, и runner повторяет его код выхода.
- Уровень доступа к дополнительному корню имеет три состояния: новая регистрация по умолчанию получает `inherit` (следует режиму сеанса), `--read-only` запрещает запись в любом режиме (включая Full-access; единственное исключение — однократное повышение прав, одобренное пользователем для отдельного вызова, см. [ADR-0036](./docs/decisions/ADR-0036-approved-escalation-override.md)), а `--read-write` в сеансе только для чтения всё равно разрешает запись (это вопрос права записи, а не ограничения на чтение; [ADR-0017](./docs/decisions/ADR-0017-three-state-root-access-and-sandbox-modes.md)). Уже запущенные процессы и постоянные терминалы сохраняют deny-набор, с которым были запущены, — терминал, запущенный до того, как корень стал доступен только для чтения, остаётся неограниченным до перезапуска; изменения cap/access действуют только на последующие вызовы и новые процессы ([ADR-0013](./docs/decisions/ADR-0013-per-root-and-per-tool-access.md)); хост, предоставляющий workingDirectory, может использовать дополнительный корень как рабочий каталог для последующих инструментов, при этом исходный проект сеанса и идентичность регистрации не меняются ([ADR-0012](./docs/decisions/ADR-0012-session-origin-and-effective-cwd.md)).
- **На Linux-хостах, где вышестоящий код выбрал Landlock, ограниченному Full-access нужен bwrap**: allowlist Landlock не умеет выражать «всё доступно для записи, кроме этих корней», поэтому такая комбинация переключается на bubblewrap, который выстраивает границу запрета записи; на хосте без рабочего bwrap (не установлен или отключены непривилегированные userns) команда Full-access с любой границей запрета записи (корень только для чтения или защищённый `$DSH_HOME`) завершается отказом до запуска. Включите bwrap или избегайте явных корней только для чтения в режиме Full-access на таком хосте ([ADR-0017](./docs/decisions/ADR-0017-three-state-root-access-and-sandbox-modes.md)).
- Дерево файлов дополнительных корней реализуется через **переключатель корня на вкладке Files**: вход в заголовке перечисляет основной корень и все дополнительные, рядом по-прежнему отображается полный путь выбранного корня; при выборе дополнительного корня область дерева захватывает побайтовая копия дерева Files из вышестоящего кода (ленивая загрузка каталогов, нативные строки и значки, автообновление по watch, открытие файла по щелчку во встроенном просмотрщике хоста, ручное обновление на прежнем месте в заголовке), а кнопка «Открыть в приложении» справа в заголовке одновременно заменяется побайтовой копией вышестоящего элемента управления и открывает выбранный корень, а не основной; при возврате к основному корню восстанавливается нативный вид, а диалог снова становится чисто управляющим. Для строк дополнительных корней также доступны те же контекстные меню, что и для основного корня (строки файлов и каталогов; дерево навигации Folder в предпросмотре файла тоже работает), а для выбранного корня — поиск по рабочему пространству (кнопка поиска в шапке, строка поиска, дерево результатов с подсветкой совпадений, всплывающее окно настроек и фильтрация скрытых элементов); и то, и другое появляется только там, где хост предоставляет соответствующую структуру — контекстные меню строк требуют `useContextMenu` (начиная с `0.2.2-alpha.3`), поиск требует `workspaceFiles.search` (начиная с `0.2.2-rc.2`), а на более старых хостах меню строк не привязываются и вход поиска не отрисовывается, вид остаётся прежним. Этот захват зависит от DOM-хуков `data-*` вышестоящего кода и при их несовпадении молча деградирует до нативного вида ([ADR-0015](./docs/decisions/ADR-0015-files-tab-plugin-owned-browsing.md), [ADR-0016](./docs/decisions/ADR-0016-files-tab-native-tree-fork.md)). LSP инициализирует отдельное рабочее пространство по корню, в котором находится дополнительный файл; от хоста требуется настройка соответствующего языкового сервера ([ADR-0011](./docs/decisions/ADR-0011-multi-root-workspace-consumers.md)). Известные границы: нативная комбинация Files **Cmd+P** по-прежнему фокусирует нативное поле поиска, скрытое захватом, поэтому нативная комбинация не считается входом в поиск по дополнительным корням — ни поиск на странице Files, ни поиск в навигаторе предпросмотра на неё не реагируют ([ADR-0041](./docs/decisions/ADR-0041-additional-root-workspace-search.md), [ADR-0043](./docs/decisions/ADR-0043-additional-root-preview-navigator-search.md)); история поиска навигатора предпросмотра сохраняется по `(pane, root)` и отделена от `(tab, root)` страницы Files, поэтому запрос страницы Files в той же панели не переносится в предпросмотр; текущая строка результата только помечается, но не прокручивается автоматически; закрытие Folder или смена корня в той же панели отбрасывает несохранённый черновик настроек ([ADR-0043](./docs/decisions/ADR-0043-additional-root-preview-navigator-search.md)).
- Когда сторонний плагин захватывает всю вкладку Files (регистрирует kind `files` с `priority: "extension"`), переключатель корня и просмотр дополнительных корней недоступны; плагин один раз показывает официальное info-уведомление, после снятия захвата уведомление может появиться снова, а управление корнями по-прежнему доступно из «Папок рабочего пространства» в боковой панели и через `/workspace-folders` ([Issue #47](https://github.com/cherrchen/dsh-plugin-multi-root-workspace/issues/47)).
- Текст, который выводит команда, — на английском (у обработчика на стороне хоста нет сведений об активном языке); текст панели следует языку интерфейса и доступен на всех восьми языках, которые предлагает DSH.
- Панель «Папки рабочего пространства» — это «действие внизу боковой панели + диалог», а не отдельная полноэкранная панель: слот `sidebar.footer.action` предоставляется во всех поддерживаемых версиях, а `sidebar.panellist`/`main` — нет. Начиная с DSH `0.2.1-alpha.3` дополнительный вход также размещается в слоте `conversation.hero.options` на странице нового сеанса: он имеет ту же геометрию, что и соседние селекторы рабочего пространства и режима, без chevron, сжимается по измеренному свободному месту в строке рабочего пространства и при остатке менее 88px превращается в кнопку-значок 28×28 (контейнер options в вышестоящем коде — `flex: none`, плагин не меняет DSH, а только измеряет остаток и ограничивает себя; если проба не распознаёт структуру строки, используется запасной вариант с окном 560px); если в старом рантайме этот слот отсутствует, регистрация молча не срабатывает, а вход в боковой панели не затрагивается ([ADR-0037](./docs/decisions/ADR-0037-conversation-hero-workspace-folders-entry.md)). Скругление rail (свёрнутого состояния) у входа боковой панели имеет собственную более раннюю границу `0.1.6-alpha.2`: в 23 поддерживаемых версиях и хост, и плагин рисуют квадрат со скруглением 12px, а в двух самых старых версиях (`0.1.5-rc.2`, `0.1.6-alpha.1`) хост рисует круг, тогда как плагин — квадрат со скруглением 12px; это зафиксированное отклонение скругления (без влияния на ink и компоновку); обёртка `@media (hover: hover)` существует только в 6 версиях с новой геометрией, а плагин сознательно обходится без обёртки, поэтому на сенсорных экранах есть отличие в hover-отклике от этих версий ([ADR-0044](./docs/decisions/ADR-0044-sidebar-footer-row-alignment-and-coexistence.md)). Высота входа боковой панели следует за элементом, занимающим строку настроек в том же столбце, и зависит от структурного маркера `data-signed-out` лаунчера учётной записи (зависимость от CSS `:has()`, а не контракт слота): в 7 версиях от `0.1.7-rc.2` и более ранних сохраняется высота триггера настроек 42px; начиная с `0.2.0-rc.1` — 32px без входа / 44px со входом, rail фиксирован на 36px; при переименовании или исчезновении маркера используется 42px (размер не задаётся ошибочно) и затрагивается только высота ([ADR-0044](./docs/decisions/ADR-0044-sidebar-footer-row-alignment-and-coexistence.md)).

### Адаптация OPS

Текущая реализация доступна в виде **режима совместимости OPS (экспериментально, по умолчанию выключен, возможны ограничения)**: параметр `multi-root-ops-compatibility.enabled` задаётся в `Settings → Plugins → Multi-root Workspace`, по умолчанию `false`, и требует явного включения. Функцию разрешено включать только на DSH `0.2.*` в рамках существующей матрицы точной поддержки; на `0.1.*` она остаётся выключенной даже при ручной настройке `enabled: true`, а старый интерфейс Settings не поддерживается ([решение о диапазоне версий](./docs/decisions/ADR-0029-ops-file-authorization-and-activity-adapter.md#ops-版本范围修订2026-11-06)). При включении из интерфейса настроек нужно прочитать официальное предупреждение о рисках, отметить, что ограничения понятны, и подтвердить ещё раз; до подтверждения параметр остаётся выключенным, а отмена, закрытие окна или Esc не сохраняют включение.

- **Включено**: активируются защита выполнения OPS, live-активность и расширения Review. Полный доступ (`danger-full-access`) на проверенных платформах macOS/Linux обеспечивает соблюдение явных границ RO/cap deny с помощью ограничения на уровне ядра; в Windows при наличии deny вызовы выполнения OPS, включая чтение, консервативно отклоняются до подготовки Worker, а защищённая подготовка и легальная запись в этой комбинации пока не поддерживаются. В WW/RO при наличии хотя бы одного недоступного для записи дополнительного корня или ограничения записи на уровне инструмента весь вызов выполнения OPS, включая чтение и page, отклоняется до подготовки и выполнения. Все режимы отклоняют вызовы выполнения OPS при недоступности Registry, кроме чистого обнаружения и публикации. Запуск subprocess без домена выполнения или действующего в этот раз профиля также отклоняется, чтобы фоновая очистка не обходила границы; это может заодно отклонить сторонние фоновые процессы, но не перехватывает собственный терминал пользователя в панели.
- **Выключено**: OPS возвращается к поведению до этой адаптации и не получает этих защит — **явный дополнительный корень только для чтения может быть записан через OPS**. Обычные многокорневые функции, нативные ограничители инструментов и собственный переключатель Auto Review не затрагиваются. Уже доставленные инструкции не стираются задним числом, вызовы, уже вошедшие в защищённый домен, и запущенные процессы сохраняют прежний снимок; новые вызовы после выключения больше не активируют эту адаптацию.
- **Ограничения эксперимента**: доступен только live-индекс активности Phase A, без моста постоянных событий. При включении история OPS без live-доказательств после resume и динамические pending (replace/batch/result/bash/unknown) приводят к техническому сбою Review; диагностика вне allowlist, например `ops_status`, также подчиняется этому консервативному правилу.

Конкретные известные пробелы:

- **Обход ограничения dsh-ops на запись в явный RO (F01, историческая база)**: в версии, охваченной аудитом, под Full-access OPS Native `ops_write_file` фактически записал в явный дополнительный RO-корень, тогда как нативный fs в том же сравнении получил отказ. При включённом режиме совместимости OPS текущая ограниченная адаптация повторно проверила под Full-access, что explicit RO/cap deny действует для OPS Native и реального PTC (повторная проверка deny — [аудит §16](./docs/reviews/dsh-ops-compatibility-audit.md#16-适配后复验)); версии, объём тестирования и исходные доказательства — в [аудите совместимости](./docs/reviews/dsh-ops-compatibility-audit.md).
- **Легальная запись и инструкции подкаталогов в dsh-ops (F04/F05, историческая база)**: нерешённой остаётся проблема, когда предполётная проверка OPS отказывает в записи: под WW — дополнительным корням inherit и с фиксированным read-write, под RO — дополнительному корню с фиксированным read-write; пробел с обнаружением инструкций подкаталогов при чтении через OPS (F05) в этом раунде повторно проверен как восстановленный при включённом режиме с live-индексом и реальным AgentLoop (инструкции подкаталогов, успешно затронутых Native и PTC, попадают в следующий запрос к модели, см. [аудит §16](./docs/reviews/dsh-ops-compatibility-audit.md#16-适配后复验)); проверенные пути инструкций уровня корня и Skills не затронуты.
- **Деградация WW batch/result в Linux bwrap (F07)**: в проверенной композиции с общим Registry все `ops_batch` / `ops_result` (включая `page`), которые доходят до ветки запуска и получают действующий cache, теряют доказательство принадлежности argv из-за добавления bind после confine; исходный путь отклоняет запуск Worker с `EXECUTOR_UNAVAILABLE`. Конфликт на уровне функции воспроизведён, сквозное тестирование на Linux не проводилось; обычные RO, Landlock и контроль без cache в этот вывод не входят. Нужен интерфейс OPS для объявления cache до confine; проверенного одностороннего обходного решения в MR пока нет, см. [аудит F07](./docs/reviews/dsh-ops-compatibility-audit.md#131-n1--f07confine-后的-cache-bind-与严格证明冲突).
- **Другие границы доступности OPS**: при общем WW purge вне диспетчеризации без действующего допуска отклоняется, поэтому кэш результатов может оставаться с предупреждением; вложенные вызовы PTC и фоновый Bash также подвержены риску отказа из-за принадлежности или устаревания доказательств. В этом раунде консервативные границы отказов проверены на трёх платформах; обычная фоновая работа и очистка по-прежнему не восстановлены и отложены на неопределённый срок, см. [итоговый объём ADR-0029](./docs/decisions/ADR-0029-ops-file-authorization-and-activity-adapter.md#最终范围与无限期延后2026-11-05).

Защитные механизмы P5 в этом репозитории не меняют OPS: легальная запись в дополнительные корни всё ещё может быть ошибочно отклонена, а кэш фоновых результатов может оставаться из-за того, что очистка отклоняется; в legacy-режиме без общего Registry PTC для WW/RO также может быть отклонён до запуска процесса с исполняемым кодом. Постоянная активность остаётся выключенной: `appendPluginRecord` в DSH явно запрещает вызовы из внешних плагинов, и заменить его обычными событиями или собственной записью в журнал нельзя. Техническая приёмка P6 выполнена в ограниченном объёме; оставшиеся функции P5 и приёмка полной совместимости **отложены на неопределённый срок** и не входят в условие завершения этого этапа, а при восстановлении в будущем будут доступны только как экспериментальная возможность. Список отложенного — в [ADR-0029](./docs/decisions/ADR-0029-ops-file-authorization-and-activity-adapter.md#无限期延后清单唯一真源), объём приёмки — в [завершённом плане](./docs/plans/completed/2026-11-01-ops-compatibility-adaptation.md).

Эти экспериментальные консервативные защиты выпущены в `v0.1.15`; они не заявляют полную совместимость с OPS и не расширяют список поддерживаемых версий. Историческая повторная проверка из §16 аудита выполнялась до появления этого переключателя и относится к пути с включённым режимом; при последующих прогонах требуется явный `enabled: true`.
